The Complete Authentication Flow

GET http://localhost:5173/ 
1. Browser → Frontend
   - Load React app bundle
   - Check localStorage for existing token
   - No token found → Show login screen

2. Alex clicks "Login with Azure AD"
   - Frontend → Azure AD OAuth endpoint
   - Redirect: https://login.microsoftonline.com/...
   
3. Azure AD → Alex's Browser
   - MFA challenge (phone approval)
   - Consent screen
   
4. Alex approves → Azure AD
   - Generate authorization code
   - Redirect: http://localhost:5173/callback?code=xxx
   
5. Frontend → Backend
   POST /api/v1/auth/callback
   Body: { code: "xxx" }
   
6. Backend → Azure AD
   POST https://login.microsoftonline.com/token
   Exchange code for access token
   
7. Backend validates token claims
   - Extract: email = alex.admin@company.com
   - Extract: groups = ["ENV_ALL_ADMINS"]
   
8. Backend → Database
   SELECT * FROM users WHERE email = $1
   
9. Database check:
   - User exists? YES
   - Role: admin
   - Teams: [] (admin sees all)
   
10. Backend generates JWT
   - Claims: { userId, role: "admin", exp: 24h }
   - Sign with HS256 secret
   
11. Backend → Frontend
   Response: { token: "eyJhbG...", user: {...} }
   
12. Frontend stores token
   - localStorage.setItem('authToken', token)
   - Axios default header: Authorization: Bearer xxx
   
13. Frontend navigates
   - Role check: admin = true
   - Redirect: /admin/governance (Issue #4 fix!)
   - NOT /dashboard (normal users go there)

Orphan Product Detection Logic

GET /api/v1/products?page=1&limit=20 
1. Frontend component: OrphanProductManager.tsx
   - useEffect hook triggers on mount
   - Calls: getProducts(page=1, limit=20)
   
2. Frontend → Backend
   GET /api/v1/products?page=1&limit=20
   Headers: { Authorization: Bearer xxx }
   
3. Backend: products.service.ts
   - Validate JWT
   - Extract user role (admin)
   - Call repository layer
   
4. Backend → Database
   SELECT 
     p.*,
     t.name as owner_team_name
   FROM products p
   LEFT JOIN teams t ON p.owner_team_id = t.id
   LIMIT 20 OFFSET 0;
   
5. Database returns 20 products
   Example rows:
   {
     id: "payment-api:env:Global",
     name: "payment-api",
     owner_team_id: null,           ← ORPHAN!
     environment: "Global"
   },
   {
     id: "customer-api:env:Global",
     owner_team_id: "team-legacy",
     environment: "Global"
   }
   
6. Backend → Frontend
   Response: {
     products: [...],
     pagination: {
       page: 1,
       limit: 20,
       total: 1435,
       totalPages: 72
     }
   }
   
7. Frontend: OrphanProductManager (client-side filtering)
   const orphans = products.filter(p => {
     const teamIds = new Set(teams.map(t => t.id));
     return !p.ownerTeamId || 
            !teamIds.has(p.ownerTeamId) ||
            p.ownerTeamId === 'legacy-pool';
   });
   
   Result: 12 orphans found in first page
   
8. Frontend renders
   - Table with 12 rows
   - Checkboxes for selection
   - Stats: "Showing 12 of 12 orphans"
Performance Note: Issue #2 & #3 fix - we now use server-side pagination (20 items/page) instead of fetching all 1435 products at once. 95% faster initial load!

Client-Side Filtering (Issue #3 Enhancement)

1. Alex types in search box
   - onChange event fires
   - State update: setSearchQuery("payment")
   
2. React useMemo hook recalculates
   const filteredProducts = useMemo(() => {
     let filtered = products; // 12 orphans
     
     if (searchQuery) {
       const query = searchQuery.toLowerCase(); // "payment"
       filtered = filtered.filter(p =>
         p.displayName?.toLowerCase().includes(query) ||
         p.name.toLowerCase().includes(query) ||
         p.id.toLowerCase().includes(query)
       );
     }
     
     if (envFilter !== 'ALL') {
       filtered = filtered.filter(p => 
         p.environment === envFilter
       );
     }
     
     return filtered;
   }, [products, searchQuery, envFilter]);
   
3. Filtered result: 3 products
   - payment-api
   - payment-gateway-v2
   - legacy-payment-service
   
4. Table re-renders
   - Only 3 rows visible
   - Stats update: "Showing 3 of 12 orphans"
   
5. No network call!
   - Filter is client-side for speed
   - All orphans already fetched

The Grand Assignment Journey

1. Alex clicks "Assign Selected"
   Button handler: handleAssign()
   
2. Frontend validation
   - Check: targetTeamId not empty? ✓
   - Check: selectedIds.size > 0? ✓ (3 products)
   
3. Show loading toast
   toast.loading("Assigning 3 products...")
   
4. Frontend → Backend (3 parallel requests)
   Promise.all([
     updateProduct("payment-api:env:Global", {
       ownerTeamId: "team-payments"
     }),
     updateProduct("payment-gateway-v2:env:Global", {
       ownerTeamId: "team-payments"
     }),
     updateProduct("legacy-payment-service:env:Global", {
       ownerTeamId: "team-payments"
     })
   ])
   
   Each calls:
   PUT /api/v1/admin/products/:id
   Body: { ownerTeamId: "team-payments" }
   
5. Backend (×3): products.service.ts
   - Validate JWT (is admin?)
   - Validate team exists
   
   Query: SELECT id FROM teams WHERE id = $1
   Result: team-payments exists ✓
   
6. Backend → Database (×3)
   UPDATE products 
   SET 
     owner_team_id = 'team-payments',
     updated_at = NOW()
   WHERE id = $1
   RETURNING *;
   
7. Database executes (×3)
   - Row 1 updated: payment-api
   - Row 2 updated: payment-gateway-v2  
   - Row 3 updated: legacy-payment-service
   
8. Backend → Event Bus (×3)
   eventBus.emit('product.assigned', {
     productId: "payment-api:env:Global",
     teamId: "team-payments",
     adminId: "alex@company.com"
   })
   
9. Event listeners react
   - Audit log service: Write to audit_log table
   - Notification service: Email Payments Team
   - Analytics: Track assignment metric
   
10. Backend → Frontend (×3)
    Response: 200 OK
    Body: { success: true, product: {...} }
    
11. Promise.all resolves
    - All 3 succeeded
    
12. Frontend updates UI
    - toast.success("3 products assigned")
    - Clear selected IDs
    - Fetch fresh product list (orphans now 9)
    
13. New API call
    GET /api/v1/products?page=1&limit=20
    Returns 20 products, now only 9 orphans
    
14. Table re-renders
    - Payment products gone from orphan list
    - Stats: "Found 9 unassigned APIs"

👩‍💻 Paula the Producer: Publishing Her First API

Meet Paula: Senior developer on the Customer Team. She's built a new "Customer Profile API" in .NET and needs to make it available in Azure APIM across DEV, QA, and eventually PROD. Before the self-service portal, this meant submitting tickets and waiting weeks. Now she can do it herself.

The Onboarding Wizard: Actual System Steps

1
Step 1: Prerequisites Check

Paula's Action: Paula starts by reviewing the prerequisites. She confirms her API is hosted in the enterprise network and that she has the necessary ADO project permissions.

Actual Component: OnboardingPrerequisitesStep.tsx

🔧 Technical Details (Access & Compliance)
1. System checks: Is API reachable?
2. Permission verification: az login --> ADO PAT validation.
3. User must click "I understand and comply" to proceed.
2
Step 2: Establish Identity

Paula's Action: Paula types "Customer Profile" for the display name. She then searches for her existing App Registration by name using the integrated search box. She selects the correct identity from the dropdown.

Actual Component: OnboardingIdentityStep.tsx

🔧 Technical Details (App ID Binding)

Step 3: Define Contract (Spec Studio)

Paula's Action: She pastes her OpenAPI YAML into the embedded Spec Studio. The system instantly parses it, showing her the detected operations (GET /profile, POST /profile/update) and a governance score.

Actual Component: OnboardingSpecStep.tsx integrating SpecStudio

🔧 Technical Details (Sparsing & Linting)
1. Spec Parsing: Extraction of methods, paths, and operation IDs.
2. Governance: Spectral linting executed locally in useSpecStudio hook.
3. Score: Displayed as "VALIDATED" or "IMPROVEMENTS RECOMMENDED".

5
Step 5: Fulfillment & Sage Execution

Paula's Action: A final summary of all configurations is displayed. Once she clicks "Provision Resources", she sees a real-time progress bar of the orchestration.

2. Saga 1: Create/Update ADO Repository.
3. Saga 2: Configure APIM Product & API resources.
4. Saga 3: Deploy Policy snippets via YAML to Git.
